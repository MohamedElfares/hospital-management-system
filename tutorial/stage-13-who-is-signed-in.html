Step 01

Loading a user by id, through the users module

Every request after sign-in carries an access token, and the token holds only a user id. Turning that id back into an account is a lookup by primary key, and the auth module may not query the users table itself: as in Stage 12, it goes through the users service, so the users module keeps a single way in.

The lookup returns deactivated users too. Deciding what deactivation means is the caller's job: auth will turn them away, but staff administration, later in this milestone, must still find a deactivated account to reactivate it.

What your code has to do
  1. Add a users-repository function that finds a user by primary key and returns None, not an error, when no account has that id.
  2. Add a users-service function on top of it, and say in its docstring that inactive users are returned too, and why.
  3. Use the session's primary-key lookup rather than a select, so a user this session already loaded costs no second query.
  4. Test a found user, an unknown id, and an inactive user, with a decoy user saved first, so a lookup that ignored the id would return the wrong row.
  5. Empty the session before each lookup, so the result comes from the database and not from memory.

Step 02

From a token to an active user

The access token is signed, so the server can trust the id inside it. But a signature only proves who the user was when the token was issued. A token stays valid for its whole 15 minutes, so without a database read a deactivated user could keep working until it ran out; with the read, deactivation applies to their very next request.

The checks run in order: decode first, because it needs no database, so a forged or garbage token never costs a query; then load the user; then refuse a missing or deactivated account. Every failure gets the same error and message as an expired token, so a token holder can't tell a deactivated account from an old token.

What your code has to do
  1. Decode the token before touching the database, and let the decoder's error pass through unchanged.
  2. Load the user through the users service, and raise one AuthenticationError when the account is missing or inactive.
  3. Use the same message the decoder uses, kept in one module constant, so a deactivated account looks exactly like an expired token.
  4. Ignore must_change_password here: the current-user route must keep working while a change is due. A later stage of this issue puts that gate somewhere else.
  5. Write nothing and commit nothing: this runs on every request.

backend/app/modules/auth/service.py 
def get_authenticated_user(session: Session, access_token: str) -> User:
    """Return the active user an access token belongs to.

    Returns:
        The user the token names, who exists and is active.

    Raises:
        AuthenticationError: If the token is invalid or expired, names no
            existing user, or names a deactivated user. The message is the
            same in every case.
    """
    user_id = decode_access_token(access_token)
    user = get_user_by_id(session, user_id)

    if user is None or not user.is_active:
        raise AuthenticationError(_INVALID_TOKEN)

    return user

Step 03

Proving the order, with a spy

The error alone can't show that decoding runs first. Code that swallowed the decode error and then looked up a made-up id would also end in the generic 401, so a test that only checks the error passes either way. A spy on the lookup sees the difference: for a garbage token it must record nothing.

An empty list could also mean the spy was patched in the wrong place and never ran. So a second test, the positive control, sends a valid token and expects exactly one lookup, by the id the token carries. Together the two tests prove what neither proves alone.

What your code has to do
  1. Write a fixture that replaces the lookup the auth service calls with a spy that records each id and then runs the real lookup.
  2. Patch it where it is looked up: in the auth service's namespace, since the service imported it by name.
  3. Test that a garbage token is rejected with no lookup at all.
  4. Add the positive control: a valid token leads to exactly one lookup, for that user's id.
  5. Test the unusable tokens (garbage, empty, a signed token for an unknown id) with an active user saved as a decoy, then a deactivated user and a user with a pending password change.
Hint — the imports this step needs

@pytest.fixture
def lookup_calls(monkeypatch: pytest.MonkeyPatch) -> list[uuid.UUID]:
    """Spy on the auth service's user lookup and return the ids it receives.

    Returns:
        The list the spy appends each looked-up id to, in call order.
    """
    calls: list[uuid.UUID] = []
    real_get_user_by_id = service.get_user_by_id

    def spy(session: Session, user_id: uuid.UUID) -> User | None:
        """Record the id being looked up, then run the real lookup."""
        calls.append(user_id)
        return real_get_user_by_id(session, user_id)

    monkeypatch.setattr(service, "get_user_by_id", spy)
    return calls

Step 04

A dependency any route can ask for

Every protected route needs the same three things before it runs: the bearer token from the header, the request's database session, and the user the service finds. A FastAPI dependency does this once, and a route asks for it with one parameter, user: CurrentUser. The dependency only connects HTTP to the service; the rules stay in the service, where they can be tested without HTTP.

OAuth2PasswordBearer reads the header. When the header is missing, or uses another scheme such as Basic, it answers 401 with WWW-Authenticate: Bearer before the service is ever called. A header that is only Bearer gives an empty token, which the decoder rejects.

What your code has to do
  1. Read the bearer token with FastAPI's OAuth2 scheme, pointing its tokenUrl at the sign-in route so Swagger UI's Authorize button works.
  2. Write a dependency that takes the token and the request's session and calls the auth service, nothing else.
  3. Export an Annotated alias, so a route needs only user: CurrentUser.
  4. Check by hand that a request without a header gets the standard error body and a WWW-Authenticate header.

# Attaches a dependency to a parameter's type.
from typing import Annotated

# Asks FastAPI to run a dependency and pass its result to the route.
from fastapi import Depends

# Reads the bearer token from the Authorization header and documents it in OpenAPI.
from fastapi.security import OAuth2PasswordBearer

# Type of the database session the service reads the user with.
from sqlalchemy.orm import Session

# Provides one database session for the request.
from app.db.session import get_db

# Auth rules; turns an access token into the active user it belongs to.
from app.modules.auth import service

# The users table's ORM model; the type of the signed-in user.
from app.modules.users.models import User

# Without the header, or with another scheme such as Basic, this answers 401
# with WWW-Authenticate: Bearer before the route runs. tokenUrl only tells
# Swagger UI's Authorize button where the sign-in form posts.
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")


def get_current_user(
    token: Annotated[str, Depends(oauth2_scheme)],
    db: Annotated[Session, Depends(get_db)],
) -> User:
    """Return the signed-in user for this request.

    Returns:
        The active user the token belongs to.

    Raises:
        AuthenticationError: From the service, if the token is invalid or
            expired or its user is missing or deactivated. The handler turns
            it into a 401 with code ``AUTHENTICATION_FAILED``.
    """
    return service.get_authenticated_user(db, token)


# Shorthand a route uses to receive the signed-in user, as ``user: CurrentUser``.
CurrentUser = Annotated[User, Depends(get_current_user)]

Step 05

Only the public fields leave the server

The current-user route returns the ORM User, which holds the password hash. A response schema decides which fields are sent: FastAPI copies only the fields of response_model into the response, so the hash can't leave by accident, even when a route returns the whole object.

The web app calls this route after every page load to learn who is signed in and whether a password change is due, so must_change_password is one of the fields. is_active isn't: anyone who can reach the route is active.

What your code has to do
  1. Add an output schema with the id, email, full name, role and must_change_password, and no password hash.
  2. Let it read values from an object's attributes, so a route can return the ORM user.
  3. Add GET /me to the auth router: Authenticated through CurrentUser, with response_model, a summary, and the 401 documented.
  4. Return the user and nothing more: the route holds no logic.

Step 06

Testing the route over HTTP

The service tests prove the rules; these prove the HTTP layer: the dependency is wired, the response is filtered, and every failure arrives in the standard error body. Most tests sign a token directly with a helper, so they don't depend on the sign-in route or pay for its password check. One test goes through sign-in on purpose, to prove the two routes agree on the key and the claims.

The success test compares the whole body with one dict. Checking a few fields would pass even if the password hash appeared alongside them.

What your code has to do
  1. Add a helper that builds an Authorization header with a freshly signed token for a user.
  2. Test 200 with exactly the public fields, and with a token from the real sign-in route.
  3. Test 401 without a header (with WWW-Authenticate: Bearer), and with a wrong scheme, a bad token and an empty one, each with its message.
  4. Test a token issued before its user was deactivated.
  5. Test that a user with a pending password change still gets 200: a later stage blocks other routes, and this test guards the exemption.
