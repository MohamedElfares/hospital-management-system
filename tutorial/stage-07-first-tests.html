Step 01

Test one behaviour, with many inputs

A test is ordinary Python that runs your code and checks the result; what makes it a test is that pytest finds it, runs it, and treats a raised exception as a failure. That is why plain assert is enough — pytest rewrites assertions so a failure prints the real values, not just "false".

Start with a pure function, because it needs no database and no application. _resolve_request_id has exactly two behaviours, so it wants two tests — not one test with six assertions, where the first failure hides the rest.

What your code has to do
  1. Cover the two behaviours separately: a valid UUID is reused and normalized, and anything else is replaced.
  2. Run the same logic over many inputs rather than copying the test body: every spelling of a valid UUID, and every kind of junk (missing, empty, containing a line break, oversized, malformed).
  3. State expected values as literals. Computing the expectation with the same transformation the code uses would let a broken implementation pass.
  4. Give unreadable cases a readable name, so the report says [oversized] instead of 100,000 characters.
  5. Name each test after the behaviour and give it a docstring saying what is expected and why it matters.
Hint — the imports this step needs
pytest.mark.parametrize
Runs one test once per input. The first argument names the parameters, the second lists the cases; each case is reported as a separate test.
pytest.param
One case, with options. id="oversized" replaces a long value in the test's name.
uuid
Parses the result. uuid.UUID(value) raises for anything that is not a UUID, which is a stronger check than comparing against the input.

Step 02

Reach the application without starting a server

A unit test cannot tell you whether the middleware is installed or the routes are reachable. For that a test has to send a request through the real application — which TestClient does in-process, with no port and no server to start.

Every such test needs a client, so building one in each test would repeat setup the way copied test bodies repeat logic. A fixture prepares what a test needs; the test asks for it by naming it as a parameter, and pytest passes it in.

What your code has to do
  1. Put shared fixtures in conftest.py, which pytest loads on its own — tests must never import from it.
  2. Build the application with the factory, so the test exercises the same wiring the server uses.
  3. Give each test its own application, so a change one test makes cannot reach the next one.
  4. Keep the client in a separate fixture that depends on the application, so a test can ask for both and get the same instance.
  5. Assert the body as well as the status: a route answering 200 with the wrong body must fail.
Hint — the imports this step needs
pytest.fixture
Marks a function as something tests can request. By default it runs once per test, so each test gets a fresh value.
TestClient
Sends requests through the application object. The response exposes status_code, json(), text and headers.

Step 03

Hold the error contract to its promise

Plan §11 promises one error shape for every failure. The tests that matter here are the ones nobody writes by reflex: an unknown URL and a wrong method never reach your code, so only a request through the whole application can show that the handlers are attached.

The same applies to the request-ID middleware. A unit test of the ID function cannot tell you that the middleware is installed; only a response header can.

What your code has to do
  1. Check that an unknown path comes back in the project's format, not FastAPI's {"detail": ...}.
  2. Check that a wrong method returns 405 and the Allow header the HTTP standard requires — it survives only because the handler copies the exception's headers.
  3. Check that every response carries an X-Request-ID, and that it is a real UUID.
  4. Check that an ID sent by the client is echoed back, which is what lets one request be followed across systems.
  5. Assert the status code first, then the body: digging into a body that is not there raises KeyError instead of failing with a clear comparison.
backend/tests/test_errors.py 
def test_unknown_path_returns_the_standard_404(client: TestClient) -> None:
    """An unknown URL is answered in the project's error format."""
    response = client.get("/nope")

    assert response.status_code == 404
    assert response.json()["error"]["code"] == "NOT_FOUND"


def test_wrong_method_returns_405_with_an_allow_header(client: TestClient) -> None:
    """A known path called with the wrong method returns 405 and ``Allow``."""
    response = client.delete("/health/live")

    assert response.status_code == 405
    assert response.json()["error"]["code"] == "METHOD_NOT_ALLOWED"
    assert response.headers["allow"] == "GET"


def test_response_carries_a_generated_request_id(client: TestClient) -> None:
    """Every response carries an ``X-Request-ID`` header, generated if needed."""
    response = client.get("/health/live")

    assert uuid.UUID(response.headers["x-request-id"])


def test_client_request_id_is_echoed_back(client: TestClient) -> None:
    """An ID the client sends is reused, so one ID spans both systems."""
    response = client.get(
        "/health/live",
        headers={"X-Request-ID": "3f2c8a1e-9b4d-4c6e-8f00-123456789abc"},
    )

    assert response.headers["x-request-id"] == "3f2c8a1e-9b4d-4c6e-8f00-123456789abc"

Step 04

Test the failure path without breaking anything

The readiness check answers 503 when the database is unreachable. Stopping a container to test that is not a test — it cannot run in CI, and it slows everyone down.

FastAPI keeps a map on the application, so a test can say "when something asks for this dependency, call that instead". The route's try wraps the query, not the dependency, so an override that raises immediately would produce a 500; the replacement must look like a session and fail when it is used.

What your code has to do
  1. Replace the session dependency for one test only, on that test's own application.
  2. Hand the route a stub that imitates just enough of a session — one method — and raises the error the route is written to catch.
  3. Raise SQLAlchemy's error, not any exception, so the test exercises the path the route actually handles.
  4. Assert the 503 and the error code, proving the route, the domain error and the handler work together.
  5. Ask for both the application and the client, so the override applies to the client's requests.
Hint — the imports this step needs
app.dependency_overrides
A dict on the application. Mapping the real dependency to a replacement changes what routes receive, with no change to application code.
SQLAlchemyError
The base class of SQLAlchemy's errors. Raising it from the stub is what the route catches before raising its own 503 error.
backend/tests/test_health.py 
class BrokenSession:
    """Stands in for a session whose queries fail."""

    def execute(self, statement) -> None:
        """Fail the way a lost connection does.

        Raises:
            SQLAlchemyError: Always, so the readiness check takes its
                failure path without a database being involved.
        """
        raise SQLAlchemyError("connection failed")
backend/tests/test_health.py 
def test_readiness_reports_unavailable_when_the_query_fails(
    app: FastAPI, client: TestClient
) -> None:
    """A failing query makes the readiness check answer 503, not 500."""
    app.dependency_overrides[get_db] = lambda: BrokenSession()

    response = client.get("/health/ready")

    assert response.status_code == 503
    assert response.json()["error"]["code"] == "SERVICE_UNAVAILABLE"

Step 05

A database the tests are allowed to ruin

Tests write. Pointed at the development database they would leave rows behind, see each other's data, and eventually delete something you wanted. They need their own database — a real PostgreSQL one, because the design depends on partial indexes, row locks and sequences that SQLite does not have (plan §13).

Two things must be true before the first test runs: the suite is connected to the right database, and its schema is up to date. Both are expensive and neither changes between tests, so both happen once per run.

What your code has to do
  1. Take the URL from a separate setting, and stop the run when it is missing rather than falling back to the development database.
  2. Build the engine once per session, and dispose of it at the end so its pooled connections are closed.
  3. Create the schema with Alembic, not from the models: production runs the same command, so a migration that drifts from the models is caught here.
  4. Run that migration in a subprocess whose DATABASE_URL is the test database — migrations/env.py reads that setting, so an in-process call would migrate the development database instead.
  5. Copy the environment and override one key; replacing it entirely would strip PATH and break the subprocess.
  6. Report Alembic's stderr when it fails, or the failure reads "non-zero exit status 1" and nothing else.
Hint — the imports this step needs
scope="session"
Builds the fixture once per run instead of once per test. A session-scoped fixture may only depend on fixtures of the same or wider scope.
yield
Splits a fixture into setup and teardown. Everything after yield runs when the scope ends, even if a test failed.
pytest.fail
Stops with your message. pytrace=False hides pytest's internals, which is right for a setup problem.
backend/tests/conftest.py 
@pytest.fixture(scope="session")
def test_engine() -> Iterator[Engine]:
    """Provide the engine for the test database, once per test run.

    Yields:
        The engine connected to the test database.
    """
    settings = get_settings()
    database_url = settings.test_database_url

    if database_url is None:
        pytest.fail("TEST_DATABASE_URL is not set", pytrace=False)

    engine = create_engine(
        database_url,
        pool_pre_ping=True,
        pool_size=5,
        max_overflow=5,
        connect_args={"options": "-c timezone=utc", "connect_timeout": 5},
    )

    yield engine

    engine.dispose()
backend/tests/conftest.py 
@pytest.fixture(scope="session")
def apply_migrations() -> None:
    """Bring the test database's schema up to date, once per test run."""
    settings = get_settings()
    database_url = settings.test_database_url

    if database_url is None:
        pytest.fail("TEST_DATABASE_URL is not set", pytrace=False)

    environment = os.environ | {"DATABASE_URL": database_url}
    backend_dir = Path(__file__).resolve().parents[1]

    result = subprocess.run(
        [sys.executable, "-m", "alembic", "upgrade", "head"],
        cwd=backend_dir,
        env=environment,
        check=False,
        capture_output=True,
        text=True,
    )

    if result.returncode != 0:
        pytest.fail(
            f"Alembic migration failed:\n{result.stderr}",
            pytrace=False,
        )

Step 06

One transaction per test, rolled back at the end

Deleting rows after each test is slow and easy to get wrong. Letting the database undo the work is neither: the test runs inside a transaction, and the transaction is rolled back afterwards. PostgreSQL rolls back schema changes too, so even a table created mid-test disappears.

One obstacle: services commit, and a real commit would end that transaction. SQLAlchemy can join the session to the existing transaction so each commit() releases a savepoint instead — application code commits as usual, and the outer rollback still erases everything.

What your code has to do
  1. Open a connection and a transaction per test, and give the test a session joined to that transaction.
  2. Make a service's commit() a savepoint release, so application code needs no test-specific behaviour.
  3. Tear down in order: close the session, roll back, close the connection.
  4. Point the application's database dependency at that same session, so a request made over HTTP and a query in the test see the same data.
  5. Return the session from the override without closing it — the fixture owns its lifecycle, and the test still needs it after the request.
  6. Prove it: one test creates a table, inserts a row and commits; a second test finds no trace of it.
Hint — the imports this step needs
join_transaction_mode="create_savepoint"
How the session treats the transaction it joins. Commits become savepoint releases, so the outer transaction survives to be rolled back.
text
Wraps raw SQL. Useful here because the probe tests need no models.
backend/tests/conftest.py 
@pytest.fixture
def db_session(test_engine: Engine, apply_migrations: None) -> Iterator[Session]:
    """Provide a database session whose work is undone after the test.

    Yields:
        A session bound to the test's transaction.
    """
    connection = test_engine.connect()
    transaction = connection.begin()
    session = Session(bind=connection, join_transaction_mode="create_savepoint")

    yield session

    session.close()
    transaction.rollback()
    connection.close()

def client(app: FastAPI, db_session: Session) -> TestClient:

    Returns:
        A client whose requests reach that application and that session.
    """

def test_a_row_written_in_one_test_is_not_visible_in_the_next(db_session: Session) -> None:
    """Work done through the session, including a commit, is visible in the test."""
    db_session.execute(text("CREATE TABLE IF NOT EXISTS rollback_prob (note text)"))
    db_session.execute(text("INSERT INTO rollback_prob VALUES ('first test')"))
    db_session.commit()

    rows = db_session.execute(text("SELECT COUNT(*) FROM rollback_prob")).scalar()
    assert rows == 1


def test_a_previous_test_left_no_table_behind(db_session: Session) -> None:
    """The table created and committed by the previous test no longer exists."""
    exists = db_session.execute(text("SELECT to_regclass('public.rollback_prob')")).scalar()

    assert exists is None
