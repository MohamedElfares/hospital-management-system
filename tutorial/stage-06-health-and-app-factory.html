Health checks and the app factory

Two routes tell a platform whether to restart the app or just wait — and one factory function finally turns the last three stages into an API you can open in a browser.

Before you start

What you already have

Nothing new to install. This stage is about assembling what the last two stages produced into an application you can open in a browser.

Available already
  • fastapiAPIRouter groups the health routes; Depends hands the route a database session.
  • sqlalchemyselect(1) is the readiness ping, and SQLAlchemyError is what you catch when it fails.
  • pydanticBaseModel gives the response a documented shape in /docs.
Step 01

A check that never touches the database

Two health checks answer two different questions. Liveness asks "is this process alive?", and a failure means restart the container. Readiness asks "can it serve a request right now?", and a failure means stop sending traffic for a moment, without restarting anything.

Keeping them apart matters on free hosting: Neon's compute suspends after five minutes idle, so the database is briefly unreachable. If liveness checked the database too, every nap would look like a crashed application and the platform would restart a process that was working perfectly.

What your code has to do
  1. Group both routes in a router, not a second FastAPI() application: only one application exists, and the factory in step 04 includes this router.
  2. Serve them at /health/live and /health/ready, outside /api/v1. Monitoring must not have to follow the API's versioning, and these paths must never move.
  3. Make the liveness route depend on nothing at all: no database, no settings.
  4. Return a tiny, fixed body. A public endpoint should not reveal versions, hostnames or database details.
  5. Document it for /docs: a summary, a tag and a response model, as plan §11 requires of every route.
Hint — the imports this step needs
APIRouter
A group of routes. Give it prefix="/health" and a tag once, and the application includes the whole group in one line.
BaseModel
The base class for a response model. It gives /docs the shape of the body instead of an untyped object.
backend/app/api/health.py 
router = APIRouter(prefix="/health", tags=["health"])


class HealthStatus(BaseModel):
    """Body of a successful health check.

    Attributes:
        status: Always ``"ok"``. A failing check answers with an error
            status code instead, never with a different value here.
    """

    status: str


@router.get(
    "/live",
    status_code=200,
    summary="Liveness check",
    response_model=HealthStatus,
)
def live() -> dict[str, str]:
    """Report that the process is running.

    Returns:
        ``{"status": "ok"}`` whenever the process can answer at all.
    """
    return {"status": "ok"}

Step 02

A readiness check that fails on purpose

Readiness has to prove something concrete: that a connection can be taken from the pool and used. SELECT 1 is the cheapest statement that does it, and Render points its health check at this route, so its answer decides whether a deployment receives traffic.

The failure has to be a 503, not a 500 and not a 200 with an error in the body. Monitoring reads status codes: a 200 would look healthy, and a 500 would claim your code is broken when the database is only asleep.

What your code has to do
  1. Run the ping through a session from the existing dependency, so the check uses the same engine and pool as the rest of the app.
  2. Return your small success body — not the result object, which cannot be serialized and would turn a healthy database into a 500.
  3. Catch only SQLAlchemy's errors, so a bug in your own code still surfaces as a 500 instead of being reported as a database outage.
  4. Raise a domain error for 503 rather than building a response here, so the failure comes back in the standard error format. That needs a new code and a new subclass in errors.py.
  5. Keep the driver's message out of the response; say what an operator needs and let the traceback stay in the log.
  6. Document the failure too, so /docs lists 503 next to 200.
Hint — the imports this step needs
Depends, Annotated
How a route asks for a dependency. Annotated[Session, Depends(get_db)] means "give me the request's session".
select
Builds the statement. select(1) is a valid query that touches no table.
SQLAlchemyError
The base class of every SQLAlchemy error. One except covers connection failures, timeouts and driver errors, and nothing else.
backend/app/api/health.py 
@router.get(
    "/ready",
    status_code=200,
    summary="Readiness check",
    response_model=HealthStatus,
    responses={503: {"description": "The database is not reachable."}},
)
def ready(database: Annotated[Session, Depends(get_db)]) -> dict[str, str]:
    """Report that the application can serve requests right now.

    Returns:
        ``{"status": "ok"}`` when the database answered.


    Raises:
        ServiceUnavailableError: If the database can't be reached. The
            handler turns it into a 503, and the driver's message stays in
            the log rather than in the response.
    """
    try:
        database.execute(select(1))
        return {"status": "ok"}
    except SQLAlchemyError as err:
        raise ServiceUnavailableError("The database is not reachable.") from err
backend/app/core/errors.py 
class ServiceUnavailableError(AppError):
    """A dependency the request needs is temporarily unavailable (503)."""

    status_code: int = 503
    code: str = ErrorCode.SERVICE_UNAVAILABLE

Step 03

Fail fast, or the check hangs instead of answering

A health check that hangs is worse than one that fails. The platform cannot tell "starting up" from "stuck", the request occupies a worker, and your 503 never arrives.

psycopg has no connection timeout by default. When packets are dropped rather than refused — a stopped container, a firewall, a network fault — the attempt waits for the operating system's TCP timeout. Measured on this project: over 45 seconds without a timeout, and 5.0 seconds with one.

What your code has to do
  1. Give the engine a connection timeout of a few seconds, alongside the timezone option it already passes to the driver.
  2. Keep it long enough for a suspended database to accept a connection, and short enough for a health check to answer.
  3. Leave query execution untouched: this setting bounds making a connection, not running statements.
  4. Prove it: stop the database container and time a request to /health/ready. It should answer in about the timeout, not hang.
backend/app/db/session.py 
# pool_pre_ping replaces connections that Neon dropped while its compute was
# suspended. The pool stays small because the app runs one worker and Neon's
# free plan limits connections. Forcing the session timezone to UTC makes
# PostgreSQL return timestamps in UTC, as the API contract requires.
engine = create_engine(
    url=settings.database_url,
    pool_pre_ping=True,
    pool_size=5,
    max_overflow=5,
    connect_args={"options": "-c timezone=utc", "connect_timeout": 5},
)

Step 04

An application factory, not a module-level app

One function builds the application: it configures logging, creates the app, registers the error handlers, installs the request-ID middleware and includes the routers. A module-level app = FastAPI() would work too, but it is built while the module is imported, so importing anything from it needs valid settings and every test shares one instance.

Only one ordering rule is strict: configure logging first. Records written before that are dropped or unformatted, and startup is exactly when you want to see them.

What your code has to do
  1. Build and return a fully configured application from a function, so a test can create its own with different settings.
  2. Keep a module-level app as well, because uv run fastapi dev app/main.py and the container both import it by name.
  3. Configure logging first, before the application object exists.
  4. Register the error handlers, add the middleware, and include the health router — without a prefix, since the router carries its own.
  5. Give the application a title and version; both appear in /docs and in the exported OpenAPI schema.
Hint — the imports this step needs
FastAPI
The application class. title and version are documentation, not behaviour.
register_exception_handlers, request_context_middleware, configure_logging
The three pieces from the previous stages, each doing one job and each applied here.
router as health_router
An aliased import. Every module's router is called router; renaming it on import keeps main.py readable as more arrive.
backend/app/main.py 
def create_app() -> FastAPI:
    """Build a fully configured application.

    Returns:
        An application with logging configured, the error handlers
        registered, the request-context middleware installed, and the health
        routes included.
    """
    settings = get_settings()
    configure_logging(settings.log_level)

    app = FastAPI(title="Hospital Management System API", version="0.1.0")
    register_exception_handlers(app)
    app.middleware("http")(request_context_middleware)
    app.include_router(health_router)

    return app


app = create_app()
