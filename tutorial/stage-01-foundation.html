The foundation

Before a single endpoint exists, decide what can never be committed, where the database comes from, and which rules a machine will enforce for you.

Before you start

What you need installed

Three tools, none of them project-specific. Install them once and every later stage assumes they are there.

On your machine
  • gitVersion control, and the thing that decides what leaves your laptop.
  • uvInstalls Python itself, resolves dependencies, and locks them. Install it standalone rather than inside a conda environment, so it is on your PATH everywhere.
  • dockerRuns PostgreSQL 17 locally, so no database has to be installed on the host.

A Windows note that costs an hour if you miss it: if PostgreSQL is already installed as a Windows service it will be holding port 5432, and the container will refuse to start. Stop the service, or change the published port in Step 03.

Step 01

Decide what can never be committed

A secret that reaches a public repository is not un-leaked by deleting it in the next commit — it stays in the history. So the ignore rules come first, before there is anything to leak.

The awkward part is that you need the opposite too: a committed .env.example that documents every variable without holding a single real value. One rule hides the secrets; one exception publishes the template.

What your file has to do
  1. Initialise a repository whose default branch is main.
  2. Ignore every environment file, whatever suffix it carries — .env, .env.local, .env.production — because the next one you create must be ignored without you remembering to add it.
  3. Make one exception for the committed template, so the repository still documents which variables exist.
  4. Ignore what tools generate and nobody reviews: the virtual environment, bytecode, tool caches, coverage output, and — already, for Phase 2 — node_modules and build output.
  5. Ignore your personal Claude Code settings while keeping the shared ones, so the team rules stay in the repository and your local overrides don't.
  6. Prove it: git check-ignore -v backend/.env should name the rule that catches it.
Hint — the syntax this step needs
pattern
A name or glob to ignore. .env.* covers every suffixed variant, which is what makes the rule survive files you haven't invented yet.
!pattern
An exception that re-includes a file. Order matters: the exception has to come after the rule that excluded it.
dir/
A trailing slash matches directories only. Useful for .venv/ and node_modules/, so a file with the same name is not caught by accident.
git init -b main
Creates the repository with a named initial branch, instead of inheriting whatever default your Git version has.

Step 02

One line ending, whatever machine you are on

Git on Windows converts text files to CRLF on checkout by default. That is invisible until a shell script written here is run inside a Linux container and fails with a message about \r, or a whole file shows as changed because someone else opened it on macOS.

The fix is a policy committed to the repository rather than a setting each person remembers: store everything with LF, and name the few file types that genuinely need CRLF.

What your file has to do
  1. Let Git decide which files are text, and then store and check out every one of them with LF, on every operating system.
  2. Keep CRLF for Windows-only scripts (.bat, .cmd, .ps1), which is the one place it is still required.
  3. Say why in a comment: the container and CI run Linux, and entrypoint.sh will break under CRLF.
  4. Apply it to the files already committed with git add --renormalize ., since the rule is not retroactive on its own.
Hint — the attributes this step needs
text=auto
Let Git detect text files and normalise their endings, leaving binaries untouched.
eol=lf
Check out with LF regardless of platform — this is what overrides Git for Windows' default conversion.
eol=crlf
The deliberate exception, applied per file extension for scripts that Windows itself runs.
.gitattributes 
# Store and check out text files with LF endings on every OS, so shell
# scripts (entrypoint.sh) and YAML behave the same on Windows and in Linux
# containers and CI.
* text=auto eol=lf

# Windows-only scripts keep CRLF.
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

Step 03

A database you can throw away

The design depends on PostgreSQL features — partial unique indexes, row locks, sequences — so development has to run on the real thing, at the same major version as production. A container gives you that without installing a database on your machine, and lets you delete the whole thing and start over when an experiment goes wrong.

Credentials here are deliberately boring. They are development defaults, not secrets, and production never reads this file.

What your file has to do
  1. Run PostgreSQL 17 — pinned, because "latest" would silently move under you — and bring itself back up after a reboot.
  2. Take its user, password and database name from variables with local defaults, so a teammate can override them without editing the file.
  3. Publish the port only on the loopback address, so the development database is not reachable from the network you happen to be on.
  4. Let the port itself be overridden, for the case where something already owns 5432 on this machine.
  5. Keep data in a named volume, so stopping the container doesn't lose it — and deleting the volume is an explicit act.
  6. Report when it is genuinely ready for connections, not merely started, so tooling can wait for it.
Hint — the keys this step needs
image
Which image and tag to run. Pin the major version so local, CI and production agree.
environment
Variables the image reads on first start to create the user and database. ${VAR:-default} means "take VAR if it is set, otherwise this".
ports
Publishes a container port on the host. Prefixing with 127.0.0.1: binds it to loopback instead of every interface.
volumes
Where the data lives. A named volume outlives the container and is managed by Docker.
healthcheck
A command Docker runs on a timer. pg_isready answers whether the server accepts connections; the doubled $$ escapes the variable so Compose passes it through to the shell.
docker-compose.yml 
# Local development services. Start the database with: docker compose up -d db
# The credentials are development-only defaults; override them with shell
# variables if needed. Production uses Neon, never this file.

services:
  db:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-hms}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-hms}
      POSTGRES_DB: ${POSTGRES_DB:-hms}
    ports:
      # Bound to localhost only, so the dev database isn't exposed on the network.
      - "127.0.0.1:${POSTGRES_PORT:-5432}:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      # Lets other services (and CI) wait until PostgreSQL accepts connections.
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  pgdata:

Step 04

The Python project

uv creates the project, installs a pinned Python, and records exact versions in uv.lock so CI and your machine resolve to the same tree. One flag matters more than it looks: recent uv versions set a project up as an installable package by default, which produces a src/ layout this project doesn't use.

Dependencies split in two. Runtime packages ship to production; development tools — the test runner, the linter, the hooks — stay out of the image.

What your project has to do
  1. Create the project in backend/, pinned to Python 3.13, with a flat layout — application code will live in backend/app/, so there must be no src/ folder and no build backend.
  2. Install what the API needs at runtime: the web framework with its standard extras, the ORM, the PostgreSQL driver, the migration tool, and typed settings.
  3. Install the timezone database as a package, because Windows has no system copy and the settings validator will need one.
  4. Install the development-only tools separately: test runner, coverage, linter, hook runner, and a fake-data library.
  5. Commit uv.lock. It is what makes an install reproducible; leaving it out defeats the point of the lockfile.
  6. Delete whatever sample module uv init generated — the entry point will be app/main.py later.
Hint — the commands and packages this step needs
uv init --app --no-package
Creates an application, not a library. Without --no-package, current uv versions add a src/ layout and a build backend you would then have to unpick.
uv add
Adds a runtime dependency, resolves it, and writes both pyproject.toml and uv.lock.
uv add --dev
Adds a development dependency into a separate group, so production installs skip it.
fastapi[standard]
The framework plus the extras you will actually use: the fastapi CLI, uvicorn, and httpx — which the test client needs later.
psycopg[binary]
PostgreSQL driver, prebuilt. The binary extra avoids needing a C toolchain to install it.
tzdata
The IANA timezone database as a package. On Linux zoneinfo reads the system copy; on Windows there isn't one.

Step 05

Let the linter enforce the rules you agreed to

This project asks for a docstring on every module, class and function, and one imported name per line so each import can carry its own comment. Rules like that decay unless something checks them, so they go into configuration now — while there are two files to fix, not two hundred.

Two directories are exempt. Migrations are generated, and forcing docstrings on them is noise; tests don't need module-level docstrings, since the test names and their own docstrings carry the meaning.

What your configuration has to do
  1. Lint and format for Python 3.13, with a line length the whole team shares.
  2. Turn on the docstring rules and import sorting on top of Ruff's defaults, and tell it which docstring convention the project follows.
  3. Force one imported name per line, so every import can be preceded by the one-line comment the project requires.
  4. Exempt migrations from docstring rules entirely, and exempt tests from the module and package docstring rules only.
  5. Point pytest at the tests directory, and make app importable from the project root — necessary because the project is not installed as a package.
  6. Run uv run ruff check . and read what it says. On an empty project it should pass; from the next stage it will start asking for docstrings.
Hint — the settings this step needs
extend-select
Adds rule families to the defaults. D is pydocstyle (docstrings), I is isort (import order).
pydocstyle.convention
Chooses the docstring dialect so Ruff checks Google-style Args and Returns sections and switches off the rules that contradict it.
isort.force-single-line
One name per import line. Without it Ruff merges imports and the comment above only describes the first name.
per-file-ignores
Relaxes rules by path. D100 is a missing module docstring, D104 a missing package docstring.
pythonpath
Adds a directory to sys.path for pytest. Needed because --no-package means app is never installed into the environment.
backend/pyproject.toml 
[tool.ruff]
target-version = "py313"
line-length = 100

[tool.ruff.lint]
extend-select = ["D", "I"]  # D: docstrings, I: import sorting

[tool.ruff.lint.pydocstyle]
convention = "google"

[tool.ruff.lint.isort]
force-single-line = true  # one imported name per line

[tool.ruff.lint.per-file-ignores]
"migrations/**" = ["D"]
"tests/**" = ["D100", "D104"]

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]  # the project isn't installed as a package, so make `app` importable

Step 06

Run the checks before the commit, not after the push

CI will run these same checks, but finding out ten minutes later — on a branch you have already pushed — costs a fix-up commit every time. A hook runs them while the change is still in your working tree.

Keep the hook set small and boring: hygiene that catches accidents, plus the same linter CI uses. Hooks that reformat the world or make opinionated edits turn into something you disable, and a disabled hook protects nothing.

What your configuration has to do
  1. Catch the accidents that are hard to notice in a diff: trailing whitespace, a missing final newline, broken YAML or TOML, merge-conflict markers, and oversized files.
  2. Refuse a commit that contains a private key — the one hook here that is about security rather than tidiness.
  3. Run the same linter and formatter as CI, limited to the backend, so a hook never trips over files it has no opinion about.
  4. Pin every hook repository to a tag. Floating versions mean a commit can start failing because someone else released something.
  5. Install the hook once with uv run pre-commit install, then prove it with pre-commit run --all-files.
Hint — the keys this step needs
repos / rev
Where a hook comes from and which tag to use. The tag is the version pin; pre-commit autoupdate is how you move it deliberately.
hooks: id
Which hook from that repository to run. Each one is a small program with its own exit code.
files
A regular expression limiting which paths a hook sees. ^backend/ keeps Ruff away from the frontend and the docs.
args
Extra flags for the hook. --fix lets Ruff repair what it safely can; the commit still stops so you can look at the result.
.pre-commit-config.yaml 
repos:
  # General hygiene for every file in the repository.
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-toml
      - id: check-merge-conflict
      - id: check-added-large-files
      # Blocks accidental commits of private keys.
      - id: detect-private-key

  # Ruff lint (with fixes) and format, limited to the backend.
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.16.8
    hooks:
      - id: ruff-check
        args: [--fix]
        files: ^backend/
      - id: ruff-format
        files: ^backend/
