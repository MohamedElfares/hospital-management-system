Step 01

One password rule for every way a password is set

Plan §8.1 sets one rule: 12 to 128 characters, with no composition rules. Until now it lived on UserCreate.password. Changing a password needs the same rule, and resetting one will too, so the rule moves into a type of its own that every schema uses. The limits are exported, so the CLI's message and the tests are built from them and can't fall behind the rule.

The type is a SecretStr, so a model holding a password shows ********** when it is printed or logged.

What your code has to do
  1. Define the two limits as module constants, and a reusable annotated type that applies them to a SecretStr.
  2. Use it for UserCreate.password, so the create-admin rule doesn't change.
  3. Build the CLI's password message from the constants.
  4. Run the users and CLI tests unchanged.

Step 02

The request: two passwords, two different limits

The new password follows the shared rule. The current password only has a maximum: it is checked against the stored hash, not against the rule, so a minimum would add nothing, while the maximum caps the Argon2 work, since no stored password can be longer than 128 characters.

Whether the current password is right, and whether the new one differs from it, depends on the stored hash, so the schema doesn't try. The service checks both.

What your code has to do
  1. Add a request schema with the current password (a maximum only) and the new one (the shared rule).
  2. Keep both values exactly as typed, spaces included.
  3. Test both limits of the new password, on each side; a one-character current password; and a current password over the maximum.
  4. Test that str and repr of the whole model hide both passwords.

Step 03

A new password, and a fresh start

The user must prove they know the current password, so a stolen access token alone can't take over the account. The new password must differ from the current one, which is checked with verify_password: Argon2 salts every hash, so two hashes of the same password never match. Both refusals are 400, not 401, because the web app treats a 401 as an expired session and would sign the user out.

On success the new hash replaces the old one, the forced-change flag is cleared, every refresh token of the user is revoked, and this device gets a new session with a fresh 7-day window (ADR-0004). The order matters: revoking runs before issuing, because the session flushes the new row before the bulk UPDATE runs, and the UPDATE would then revoke the new token too.

What your code has to do
  1. Unwrap each password once, by name, into a local: verify_password and hash_password need a plain str.
  2. Raise a 400 for a wrong current password, and another for a new password that verifies against the current hash.
  3. Store the new hash and clear must_change_password.
  4. Revoke every token of the user, then issue a new pair expiring 7 days from now.
  5. Commit once, and leave last_login_at alone.

def change_password(session: Session, user: User, data: PasswordChange) -> IssuedTokens:
    """Change the signed-in user's password and start a fresh session.

    Returns:
        The new session's access token and refresh token.

    Raises:
        BadRequestError: If the current password is wrong, or the new
            password is the same as the current one. Nothing is saved.
    """
    current_password = data.current_password.get_secret_value()
    new_password = data.new_password.get_secret_value()

    if not verify_password(current_password, user.password_hash):
        raise BadRequestError("Current password is incorrect.")

    if verify_password(new_password, user.password_hash):
        raise BadRequestError("The new password must be different from the current one.")

    now = datetime.now(UTC)
    expires_at = now + timedelta(days=get_settings().refresh_token_expire_days)

    user.password_hash = hash_password(new_password)
    user.must_change_password = False

    # Revoke before issuing: the bulk UPDATE would otherwise also revoke the
    # new token, which autoflush has already written to the table.
    repository.revoke_all_for_user(session, user.id, now)

    issued_tokens, _ = _issue_tokens(session, user, expires_at)

    # TODO(1.3): audit password changes (plan §8.6)

    session.commit()

    return issued_tokens

Step 04

Testing the change, and every refusal

The success tests check each thing the change writes: the hash, the flag, the revoked sessions, the new session's expiry from both sides, and that all of it is committed. The commit test rolls back first, which also makes the user reload from the database, so it reads what was saved rather than what is still in memory.

A refused change must write none of those things. The test compares the stored hash with the one from before instead of verifying the old password: in the reuse case the “new” password is the old one, so a hash wrongly rewritten from it would still verify.

What your code has to do
  1. Add a helper that builds a valid change for the test user, replacing only the value a test is about.
  2. Test the new hash, the cleared flag, every old session revoked, and a new session expiring between two bounds.
  3. Roll back after the change and check that the password, the flag and the new session were saved.
  4. Parametrize the two refusals: each raises its message and leaves the hash, the flag and the tokens exactly as before.
  5. Test that another user's token and hash are untouched.

Step 05

The endpoint: a body and a new cookie

POST /auth/change-password is Authenticated. The user comes from the access token, so a caller can only change their own password, and the passwords come from a JSON body: the form that sign-in uses has no field for a new password. The route calls the service, sets the new refresh cookie and returns the new access token.

Setting the cookie is not optional. The service has just revoked every token, including the one in this browser's cookie; without the new cookie, this device would be signed out within 15 minutes, when its access token runs out. A refused change sets no cookie, so the browser keeps the one that still works.

What your code has to do
  1. Add the route under the router's prefix, with the body, the signed-in user, the response and the session.
  2. Document the 400 and the 401; the 422 is documented automatically.
  3. Set the new refresh cookie with set_refresh_cookie, and return the access token.
  4. Test exactly one Set-Cookie header with the security flags, that the old cookie is refused, that only the new password signs in, and that a refusal is a 400 with no Set-Cookie.
  5. Test the 422 cases, and that no password sent appears in the response.

Step 06

A false alarm, and a narrower rule

Testing the change with two devices exposed a flaw in Stage 14's rule. A user changes their password on a laptop while a phone still holds its old cookie, which the change revoked. The phone refreshes in the background, and refresh takes the revoked token for a stolen copy and revokes every session, including the laptop's brand-new one. The user is signed out on the device they just used, and the security log records a false alarm.

Only a rotated token proves a copy exists: it was already exchanged, so whoever presents it kept a copy. A token revoked any other way, by sign-out, a password change, deactivation or an earlier alarm, has no replacement. The server ended it on purpose, so it is refused like any other unusable token, with no alarm (ADR-0004).

What your code has to do
  1. In refresh's revoked branch, raise the plain error straight away when the token has no replaced_by_id.
  2. Keep the alarm, the mass revocation and the commit for rotated tokens, and keep the revoked check before the expiry check.
  3. Move the reuse tests onto a helper that saves a properly rotated token, with both revoked_at and replaced_by_id set.
  4. Test that a token revoked without rotation is refused, logs nothing, and leaves the other session active.
  5. Test the two devices over HTTP: the phone refreshes first and gets 401, and the laptop's new cookie still gets 200.

Step 07

The gate, on by default

While must_change_password is set, every endpoint except the current-user, refresh, sign-out and change-password routes must answer 403 PASSWORD_CHANGE_REQUIRED (plan §8.1), so a temporary password that was shared or written down can't be used for real work. Putting the check inside CurrentUser makes it fail closed: every route that asks for the signed-in user is gated, and a new route can't forget it.

The three routes the change itself needs opt out by asking for CurrentUserAllowingPasswordChange, so the exemption is visible in the route's signature. The gated dependency builds on the base one, so a bad token or a deactivated account still gets a 401 first; only a valid, active user can get the 403. FastAPI runs the base dependency once per request, so the user is loaded once.

What your code has to do
  1. Put the rule in a service function that raises a 403 with code PASSWORD_CHANGE_REQUIRED when the flag is set.
  2. Rename the existing dependency to say it skips the gate, and add a new get_current_user that depends on it and calls the service check.
  3. Keep CurrentUser as the gated alias, and add the exempt alias beside it.
  4. Switch /me, /logout and /change-password to the exempt alias; /refresh uses no access token and needs nothing.
  5. Test the service function both ways.

    """Return the signed-in user, even while a password change is pending.

    Returns:
        The active user the token belongs to.

    Raises:
        AuthenticationError: From the service, if the token is invalid or
            expired or its user is missing or deactivated. The handler turns
            it into a 401 with code ``AUTHENTICATION_FAILED``.
    """
    return service.get_authenticated_user(db, token)


def get_current_user(
    user: Annotated[User, Depends(get_current_user_allowing_password_change)],
) -> User:
    """Return the signed-in user, refusing one who must change their password.

    Returns:
        The same user, who has no password change pending.

    Raises:
        PermissionDeniedError: From the service, if ``must_change_password``
            is set. The handler turns it into a 403 with code
            ``PASSWORD_CHANGE_REQUIRED``.
    """
    service.ensure_password_change_not_pending(user)

    return user


# Shorthand a route uses to receive the signed-in user, as ``user: CurrentUser``.
# Blocked while a password change is pending; the default for every route.
CurrentUser = Annotated[User, Depends(get_current_user)]

# The same user without the password-change gate, only for the routes the
# change itself needs: /auth/me, /auth/logout, and /auth/change-password.
CurrentUserAllowingPasswordChange = Annotated[
    User,
    Depends(get_current_user_allowing_password_change),

Testing a gate no route uses yet

Every route that uses CurrentUser so far is exempt, so the tests need one that isn't. A fixture adds a route to the test's own application, which the client fixture is bound to: it goes through the real middleware and error handlers, never exists outside the test, and can't leak into another test, because each test builds a fresh application.

A positive control proves the route works for a user without a pending change, so the 403 comes from the gate and nothing else. The tests from earlier stages that check /me, /logout and /change-password still work while a change is pending now guard the exemptions: switch one of those routes back to CurrentUser and its tests fail.
