CI and a protected main

The checks you already run, made unavoidable: one workflow, dependency updates that arrive as pull requests, and a branch that refuses anything unverified.

.github/workflows/ci.yml new .github/dependabot.yml new
Before you start

What you already have

Nothing to install. GitHub Actions runs on GitHub's machines and is free for public repositories, and the checks the workflow runs are the ones already in the project: Ruff, Alembic and pytest.

Available already
  • GitHub ActionsRuns a workflow on GitHub's runners whenever something happens in the repository — here, a pull request or a push to main.
  • DependabotBuilt into GitHub. Reads one config file and opens pull requests when a dependency, action or image has a newer version.
  • RulesetsRepository settings that decide what main accepts: which checks must pass, and whether a pull request is required at all.
  • ghThe GitHub CLI, for reading run logs and configuring the repository without leaving the terminal.
Step 01

A workflow that runs exactly what you run

The point of CI is not to add new checks, it is to make the existing ones unavoidable. Everything in this workflow — Ruff, the migrations, pytest — is a command already run by hand; the value is that a machine runs them on every change, on a clean Linux box, without anyone remembering to.

Start with when it runs and what it is allowed to do. A token with more permission than a job needs is a standing risk, and a job with no time limit can occupy a runner for six hours before anyone notices.

What your code has to do
  1. Run on every pull request and on pushes to main, so nothing reaches the default branch unchecked — and add a manual trigger, the only way to start a run without a pull request.
  2. Give the job's token read access only: it checks out code and runs tests; it writes nothing.
  3. Cancel a superseded run: a second push to the same branch makes the first run pointless.
  4. Pin the runner image rather than ubuntu-latest, so an image change cannot alter a build without a commit.
  5. Give the job a time limit measured in minutes, not hours.
  6. Name the job deliberately — that name becomes the status check the branch protection will require.
Hint — the keys this step uses
on:
The triggers. pull_request runs the workflow from the branch being proposed; push with a branch filter runs it after a merge.
concurrency:
Groups runs. Runs sharing a group cancel each other when cancel-in-progress is set — one group per branch reference.
permissions:
Scopes the automatic token. Setting it at the top applies to every job in the file.
timeout-minutes:
An upper bound per job. GitHub's default is 360 minutes.
.github/workflows/ci.yml 
name: CI

# Runs on every pull request and on pushes to main, so a branch is never
# merged without the same checks the developer runs locally.
on:
  pull_request:
  push:
    branches: [main]
  # Lets the workflow be started by hand from the Actions tab, which is the
  # only way to run it without opening a pull request.
  workflow_dispatch:

# A new push to a branch cancels the run still in progress for it.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  backend:
    # This name is the status check the ruleset on main requires, so renaming
    # the job means updating the ruleset in the same change.
    name: backend
    runs-on: ubuntu-24.04
    # A hung step (a database that never becomes healthy, a stuck download)
    # fails in minutes instead of occupying a runner for six hours.
    timeout-minutes: 15

Step 02

A real database, not a substitute for one

The test suite talks to PostgreSQL, and plan §13 is explicit that it must keep doing so: partial unique indexes, row locks and sequences behave differently or not at all elsewhere. A runner can start containers alongside the job, so CI gets the same PostgreSQL 17 as the Compose file.

A container that is running is not the same as a database that is ready. Without a health check the first migration can arrive before PostgreSQL is accepting connections, and the job fails for a reason that has nothing to do with the change.

What your code has to do
  1. Start the same PostgreSQL version the project develops against, with the same user, password and database name as docker-compose.yml.
  2. Make the job wait until the database answers, rather than assuming a started container is a usable one.
  3. Give the job the settings the application validates at startup: both database URLs, a JWT key, the environment and the log level.
  4. Keep them as plain configuration, not repository secrets — and be able to say why that is safe here.
  5. Run every step from the backend folder instead of prefixing each command with a cd.
Hint — the keys this step uses
services:
Containers started next to the job. They are reachable on 127.0.0.1 at the ports the job maps.
options: --health-cmd
The readiness probe. The job does not start its steps until the container reports healthy.
env:
Environment variables for every step in the job. The application reads these exactly as it reads .env locally.
defaults.run.working-directory
Where run: steps execute. Set once per job instead of repeated in each step.
.github/workflows/ci.yml 
    # PostgreSQL 17 for the integration tests, matching docker-compose.yml.
    # The health check keeps the job waiting until the database accepts
    # connections, so the first migration can't run too early.
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: hms
          POSTGRES_PASSWORD: hms
          POSTGRES_DB: hms
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U hms -d hms"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10

    # Configuration for the run, not secrets: the database is a throwaway
    # container and the JWT key signs nothing that outlives the job. Real
    # values live in the Render dashboard.
    env:
      DATABASE_URL: postgresql+psycopg://hms:hms@127.0.0.1:5432/hms
      TEST_DATABASE_URL: postgresql+psycopg://hms:hms@127.0.0.1:5432/hms_test
      JWT_SECRET_KEY: ci-only-not-a-real-secret-0123456789abcdef
      ENVIRONMENT: test
      LOG_LEVEL: WARNING

    defaults:
      run:
        working-directory: backend

Step 03

Steps ordered so the cheapest failure comes first

Order matters for feedback speed. Linting takes a second and formatting takes less; tests take longer and need a database. Putting the fast checks first means an obvious mistake fails in seconds instead of after the whole suite.

Two steps here are less obvious. The test suite needs its own database, and the service container only creates the one it was told about. And alembic check earns its place by failing when the models and the migrations disagree — the forgotten-migration bug, caught before it reaches anyone.

What your code has to do
  1. Install dependencies from the lockfile, failing if the lockfile and the project file disagree — a dependency must never enter CI without being committed.
  2. Cache the dependency downloads, keyed on the lockfile.
  3. Run lint and formatting before anything that needs a database.
  4. Create the test database the suite expects; the service container only creates one.
  5. Apply the migrations, then check that none are missing.
  6. Run the tests with a coverage floor, so coverage cannot quietly fall below the number the plan sets (§13: 80%).
  7. Pin each action to an exact version where the action publishes no floating major tag.
Hint — what each step uses
actions/checkout
Fetches the repository into the runner's workspace.
astral-sh/setup-uv
Installs uv and caches downloads. cache-dependency-glob tells it which file invalidates the cache.
uv sync --locked
Installs exactly the lockfile. It fails rather than silently resolving something new.
psql
Already on the runner image. Used once, to create the database the tests connect to.
--cov-fail-under
Turns coverage into a gate instead of a number nobody reads.
.github/workflows/ci.yml 
    steps:
      - uses: actions/checkout@v7.0.1

      # Installs uv and caches the dependency downloads between runs. The
      # version is exact because this action publishes no floating major tag;
      # Dependabot raises a pull request when a newer one is released.
      - name: Install uv
        uses: astral-sh/setup-uv@v10.2.0
        with:
          enable-cache: true
          cache-dependency-glob: backend/uv.lock

      # --locked fails if uv.lock and pyproject.toml disagree, so a
      # dependency can never be added without committing the lockfile.
      - name: Install dependencies
        run: uv sync --locked

      - name: Lint
        run: uv run ruff check .

      - name: Check formatting
        run: uv run ruff format --check .

      # The test suite needs its own database; the service container only
      # creates the one named in POSTGRES_DB.
      - name: Create the test database
        run: PGPASSWORD=hms psql -h 127.0.0.1 -U hms -d hms -c 'CREATE DATABASE hms_test'

      - name: Apply migrations
        run: uv run alembic upgrade head

      # Fails when the models and the migrations disagree, which catches a
      # migration someone forgot to generate.
      - name: Check for missing migrations
        run: uv run alembic check

      - name: Run tests
        run: uv run pytest --cov=app --cov-fail-under=80

Step 04

Dependency updates that arrive as pull requests

Pinned versions stop being an advantage the moment they are forgotten: the lockfile that made builds reproducible in March is the one shipping a year-old security fix in September. Dependabot turns every update into a pull request that must pass the same CI as your own work.

The trap is volume. Ungrouped, a weekly check on four ecosystems produces a stream of single-package pull requests, and the reasonable response is to ignore them all. Grouping makes one review cover a whole ecosystem.

What your code has to do
  1. Watch each ecosystem where a version is pinned: the backend lockfile, the workflow's actions, the Compose images, and the pre-commit hooks.
  2. Point each entry at the folder that holds that ecosystem's manifest — the backend lives in a subfolder, the rest at the root.
  3. Group updates so one pull request covers an ecosystem rather than one package.
  4. Cap how many pull requests can be open at once.
  5. Prefix the commits so Dependabot's history matches the project's Conventional Commits convention.
  6. Check the ecosystem names against the current documentation rather than guessing — Docker images in a Compose file are not the same ecosystem as a Dockerfile.
Hint — the keys this step uses
package-ecosystem
Which manifest to read. uv, github-actions, docker-compose and pre-commit are separate ecosystems, each with its own file format.
directory
Where that manifest lives, relative to the repository root.
groups
Combines updates into one pull request. A group can select by pattern, by dependency type, or by update type.
.github/dependabot.yml 
version: 2

# Weekly update pull requests, grouped so one review covers a whole
# ecosystem instead of arriving one pull request per package.
updates:
  # Backend dependencies, from backend/pyproject.toml and uv.lock.
  - package-ecosystem: uv
    directory: /backend
    schedule:
      interval: weekly
      day: monday
    open-pull-requests-limit: 5
    commit-message:
      prefix: "chore(deps)"
    groups:
      python-minor-and-patch:
        update-types: [minor, patch]

  # The actions used by the CI workflow.
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
      day: monday
    commit-message:
      prefix: "chore(ci)"
    groups:
      github-actions:
        patterns: ["*"]

  # Base images in docker-compose.yml. Dockerfiles are a separate ecosystem
  # ("docker"), added in Milestone 1.2 when the production image exists.
  - package-ecosystem: docker-compose
    directory: /
    schedule:
      interval: weekly
      day: monday
    commit-message:
      prefix: "chore(docker)"

  # Hook versions pinned in .pre-commit-config.yaml, so the local checks and
  # CI don't drift apart from the tools they run.
  - package-ecosystem: pre-commit
    directory: /
    schedule:
      interval: weekly
      day: monday
    commit-message:
      prefix: "chore(deps)"

Step 05

A rule that makes the check mandatory

A green check nobody is required to wait for is a suggestion. The rule that turns CI into a gate lives in the repository, not in the workflow: a ruleset on the default branch, requiring a pull request whose named check has passed.

One detail decides whether this works: the required check is identified by the job's name. Rename the job and the branch quietly starts requiring a check that no longer exists, which blocks every merge until the ruleset is updated.

What your code has to do
  1. Require a pull request before anything reaches the default branch — with zero approvals if you work alone, since you cannot approve your own.
  2. Require the CI job's status check, by the exact name the job reports.
  3. Allow one merge method, so history stays consistent; this project squashes.
  4. Block force pushes and deletion of the default branch.
  5. Decide deliberately whether anyone may bypass the rules — and know that with no bypass, a broken CI means nothing merges until it is fixed.
  6. Verify it from the command line afterwards, rather than trusting the form you just filled in.
repository root
gh api repos/OWNER/REPO/rulesets/RULESET_ID --jq '{name, enforcement, rules: [.rules[].type], required_checks: [.rules[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context]}'
{"enforcement":"active","name":"Protect main","required_checks":["backend"],"rules":["pull_request","deletion","non_fast_forward","required_status_checks"]}

Step 06

Issues, milestones, and a board that moves itself

The plan asks for one issue per task and a board with five columns (§14). Done by hand, a board decays within a week: cards sit in the wrong column because moving them is one more thing to remember after merging.

GitHub can do the moving. The project's built-in workflows react to events — an issue closing, a pull request merging — so the board reflects the repository instead of a memory of it. Linking issues to the pull request that closes them is the other half: written correctly, merging closes all of them at once.

What your code has to do
  1. Create a milestone per plan milestone, and one issue per task, each assigned to its milestone.
  2. Create a board with the five columns the plan names, replacing the default three.
  3. Enable the built-in workflows so cards move on their own when an issue closes or a pull request merges.
  4. Link the issues from the pull request using the closing keyword before every number — a comma-separated list closes only what the keywords cover.
  5. Verify the links are real before merging, rather than after.
repository root
gh project item-list 1 --owner OWNER --format json --jq '.items[] | "#\(.content.number) [\(.status)] \(.content.title)"'
#2 [Done] FND-1: Repository, tooling and Docker Compose
#5 [Done] FND-4: Domain errors and one error format
#8 [Done] FND-7: Test infrastructure and first tests
#9 [Done] FND-8: CI, Dependabot and branch protection

Check your work

CI only proves itself by running. Open the pull request, let the workflow run, and read the result from the terminal — the same output the Actions tab shows, without leaving the shell.

repository root
gh run list --workflow ci.yml --limit 3
d567d98 pull_request success chore(docker): Bump postgres from 17 to 18
7452d03 push success feat(platform): add the Milestone 1.1 founda
af8f9df pull_request success feat(platform): add the Milestone 1.1 founda

The middle line is the one that matters most: a run triggered by the push to main, after the merge. A workflow that only runs on pull requests never verifies the merge result itself.

repository root
gh run view RUN_ID
backend: success

7. Check formatting — success
8. Create the test database — success
9. Apply migrations — success
10. Check for missing migrations — success

And the lines inside those steps, which should be the same output produced locally:

backend/
gh run view RUN_ID --log

A green run proves the checks pass on a clean machine — not that the checks are the right ones. Coverage is a floor, not a goal, and a suite that never tests permissions cannot be made to by a workflow. What CI does guarantee is that nobody, including you on a tired evening, merges a branch where these particular things are broken.
