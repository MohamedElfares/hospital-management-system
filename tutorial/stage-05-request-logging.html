Request IDs & logging

Every request gets an ID that appears in its header, its error body and its one log line, so a reported failure can be found.

app/core/logging.py new
Before you start

What you already have

Nothing new to install. Apart from FastAPI's Request and Response, everything this stage uses is in Python's standard library.

Available already
  • loggingStandard library. Writes log lines and decides, through its configuration, which ones appear and how.
  • uuidStandard library. Generates new request IDs and checks the ones clients send.
  • contextvarsStandard library. A variable that holds a separate value for each request running at the same time.
  • fastapiThe web framework. This stage uses its Request and Response in the middleware.
Step 01

A place for the ID that every request sees separately

A request ID identifies one HTTP call, not a person: Dr Sara's user ID stays the same all day, while each page she opens gets a new request ID. When she reports an error, the ID in the response points to exactly one log line.

The error handlers can read the ID from the request, but services can't, because they never receive it. A module-level variable would be shared by every request running at the same moment, so request A could log request B's ID.

What your code has to do
  1. Create one module-level variable that holds the current request's ID, with a separate value for each concurrent request.
  2. Make its value None when no request is running.
  3. Prove it: request_id_var.get() outside a request returns None.
Hint — the import this step needs
ContextVar
A per-request variable. It looks like one variable, but each running request (each task or thread) sees its own value, which is what makes it safe where a global is not.
backend/app/core/logging.py 
# Holds the current request's ID for code that has no access to the request,
# such as services and log helpers. Each concurrent request sees its own value.
request_id_var: ContextVar[str | None] = ContextVar("request_id", default=None)

Step 02

Reuse the client's ID, but only if it is a real UUID

A proxy or the web app may already have created an ID for this call. Reusing it lets one ID follow the request through every system. But the value is written to your logs, so trusting it blindly is dangerous: abc\nERROR admin deleted all patients would appear as a fake second log line, and a 10 MB header would be copied into every entry.

A valid UUID can hold neither a line break nor 10 MB. It can be spelled several ways, though, and a search only finds an ID written the same way everywhere.

What your code has to do
  1. Take the incoming header value, or None when the client sent none.
  2. Reuse it only if it is a valid UUID; otherwise generate a new random one.
  3. Normalize what you return: uppercase, braces, no dashes or a urn:uuid: prefix all come out as one lowercase, 36-character form.
  4. Prove it: {3F2C8A1E-9B4D-4C6E-8F00-123456789ABC} comes back lowercase and without braces, and a value with a line break is replaced.
Hint — the import this step needs
uuid
Generates and parses UUIDs. uuid.UUID(value) raises ValueError for anything that isn't one, which is your test; str() of the result is always the standard form.
backend/app/core/logging.py 
def _resolve_request_id(header_value: str | None) -> str:
    """Choose the ID for a request, reusing the client's only if it is a UUID.

    Returns:
        The request ID as a lowercase, 36-character UUID string.
    """
    if header_value is None:
        return str(uuid.uuid4())

    try:
        parsed = uuid.UUID(header_value)
    except ValueError:
        return str(uuid.uuid4())

    return str(parsed)

Step 03

One ID and one log line for every request

A middleware wraps every request: code before call_next runs on the way in, code after it on the way out. That is where the ID is chosen, stored, returned in a header, and where one line per request is logged (plan §12, Observability).

The log line must not contain personal data: ?q=Ahmed Hassan in a query string is a patient's name. A record ID in the path is fine, because it identifies a record, not a person.

What your code has to do
  1. Choose the ID from the X-Request-ID header and store it in both places: the request's state for the error handlers, and the per-request variable for everything else.
  2. Return it in the response's X-Request-ID header.
  3. Log one key=value line with the request ID, user ID (None until Milestone 1.2), method, path without the query string, status and duration in milliseconds.
  4. Always reset the per-request variable, whether or not the route succeeded, so no ID leaks into later work.
  5. Do the work that needs a response only once there is one: when the route crashes, there isn't.
  6. Prove it: a request to /patients?q=Ahmed Hassan logs path=/patients and nothing else of the query.
Hint — what this step uses
time.perf_counter
A precise clock for measuring durations. Subtract two readings to get the elapsed seconds.
Awaitable, Callable
Types for call_next: a function you call with the request and whose result you await.
Request, Response
The incoming request and outgoing response. You read a header from one and add a header to the other.
logging.getLogger(__name__)
This module's logger, named app.core.logging in the output, created once at module level.
backend/app/core/logging.py 
async def request_context_middleware(
    request: Request,
    call_next: Callable[[Request], Awaitable[Response]],
) -> Response:
    """Attach a request ID to each request, and log one line when it finishes.

    Returns:
        The application's response, with the ``X-Request-ID`` header added.
    """
    request_id: str = _resolve_request_id(request.headers.get("X-Request-ID"))
    request.state.request_id = request_id
    token = request_id_var.set(request_id)

    start = time.perf_counter()

    try:
        response = await call_next(request)
        response.headers["X-Request-ID"] = request_id
        duration = (time.perf_counter() - start) * 1000
        logger.info(
            "request_id=%s user_id=%s method=%s path=%s status=%s duration_ms=%.1f",
            request_id,
            None,
            request.method,
            request.url.path,
            response.status_code,
            duration,
        )
    finally:
        request_id_var.reset(token)

    return response

Step 04

Decide which log lines appear, and how

Writing a log line and configuring logging are separate jobs. The logger.info(...) calls create messages; the configuration decides which ones get through, what each line looks like, and where it goes.

Without any configuration, Python's fallback prints only warnings and errors, so every per-request INFO line from step 03 would disappear without a trace, and LOG_LEVEL from your settings would do nothing.

What your code has to do
  1. Provide one function that main.py calls once at startup, taking the level as a string such as "INFO".
  2. Put the time, level and logger name in front of every message.
  3. Make a second call replace the first configuration instead of doing nothing or adding a second handler that prints every line twice.
  4. Keep settings out of this module: the caller passes the level in.
  5. Prove it: with "INFO", an info line appears and a debug line does not.
Hint — what this step uses
logging.basicConfig
One-call logging setup. force=True removes any earlier configuration first; without it, the call is silently ignored once logging has been set up.
backend/app/core/logging.py 
def configure_logging(level: str) -> None:
    """Configure how every log record in the application is written."""
    logging.basicConfig(
        level=level,
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
        force=True,
    )
