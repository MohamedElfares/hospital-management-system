Step 01

Every failure looks the same, and takes as long

A sign-in form that answers “no such email” tells anyone with a list of addresses which ones have accounts here, and once patients have accounts (Phase 4), knowing that an email has one at a hospital is private information. So an unknown email and a wrong password must get the same error. They must take the same time too: a wrong password costs an Argon2 check, tens of milliseconds, and an unknown email that skipped it would answer almost at once, which is as easy to measure as a different message.

check_password takes the stored hash, or None when no user matched, and pays for one Argon2 check either way, against the dummy hash from Stage 10 when there is no user. What it returns in that case matters as much as what it costs: False, written out, never the result of the dummy check.

What your code has to do
  1. Accept the stored hash or None, and when it is None, still verify the password once, against the dummy hash.
  2. Return False explicitly when there is no user, whatever the dummy check says, so a missing user can never sign in.
  3. Test the right password, a wrong one, and no user.
  4. Test the cost separately from the answer: replace verify_password with a spy, and check it ran once, against the dummy hash.
  5. Time a wrong password against an unknown email.

def check_password(password: str, password_hash: str | None) -> bool:
    """Check a sign-in password, taking the same time whether or not the user exists.

    Returns:
        True only if a user exists and the password matches their hash.
    """
    if password_hash is None:
        verify_password(password, _DUMMY_HASH)
        return False

    return verify_password(password, password_hash)

Step 02

Finding the user through the users module

Sign-in needs a user by email, and the auth module may not query the users table itself: a module calls another module's service, never its repository, so the users module keeps a single way in. The lookup strips and lowercases the email, because emails are stored lowercase (Stage 09's CHECK constraint) and the form value arrives as the person typed it.

It returns deactivated users too. That looks backwards, but sign-in must check the password before it looks at is_active, so it needs the account either way. Saving the new token goes through the auth module's own repository, which adds the row and leaves the commit to the service.

What your code has to do
  1. Add a users-service function that finds a user by email ignoring case and surrounding spaces, and returns None, not an error, when nothing matches.
  2. Return inactive users too, and say why in the docstring.
  3. Add an auth repository function that registers a new token row with the session, without flushing or committing.
  4. Test the lookup with an exact email, a mixed-case email with spaces, an unknown email while another user exists, and an inactive user; test that an added token is in the table after a flush.

Step 03

The sign-in rules, and one commit

The service checks things in an order that gives nothing away: find the user, check the password, and only then look at is_active. Checking is_active first would reject a deactivated account before the Argon2 check, and the quicker answer would tell anyone who tried that email, with any password, that the account exists. Checked after the password, only someone who already knows the password can learn that the account is deactivated.

On success it saves the new token's hash, records the sign-in time, and commits once, so both are saved or neither is. It returns the two tokens in a small frozen dataclass: the router decides where each one goes, and the service never touches HTTP.

What your code has to do
  1. Look the user up through the users service, and run the password check whether or not a user was found.
  2. Raise one AuthenticationError with one message for every failure: an unknown email, a wrong password, or a deactivated account, checked in that order.
  3. On success, save a row holding only the hash, expiring REFRESH_TOKEN_EXPIRE_DAYS from now, set last_login_at, and commit once, with one clock reading for both times.
  4. Return both tokens in a frozen dataclass, not a response schema: the access token for the body, the raw refresh token for the cookie.
  5. Let a user who must change their password sign in: they need a session to change it, and a later stage of this issue blocks everything else until they do.

# One message for every failure, so no reply hints at which check failed.
_INVALID_CREDENTIALS = "Incorrect email or password."


@dataclass(frozen=True)
class LoginResult:
    """The tokens issued by a successful sign-in.

    Attributes:
        access_token: The signed JWT for the ``Authorization: Bearer``
            header, returned in the response body.
        refresh_token: The raw refresh token. It goes only into the
            ``HttpOnly`` cookie, never into a response body or a log; the
            database holds only its hash.
    """

    access_token: str
    refresh_token: str


def login(session: Session, email: str, password: str) -> LoginResult:
    """Sign a user in with their email and password.

    Returns:
        The access token for the response body and the raw refresh token
        for the cookie.

    Raises:
        AuthenticationError: If the email matches no user, the password is
            wrong, or the account is deactivated. The message is the same
            in every case.
    """
    user = get_user_by_email(session, email)

    if not check_password(password, user.password_hash if user else None):
        raise AuthenticationError(_INVALID_CREDENTIALS)

    # check_password already rejected a missing user; testing for None again
    # lets the type checker know that user is set from here on.
    if user is None or not user.is_active:
        raise AuthenticationError(_INVALID_CREDENTIALS)

    # One timestamp for both writes, so the token's expiry and the recorded
    # sign-in time agree exactly.
    now = datetime.now(UTC)
    raw_token = generate_refresh_token()

    repository.add(
        session,
        RefreshToken(
            user_id=user.id,
            token_hash=hash_refresh_token(raw_token),
            expires_at=now + timedelta(days=get_settings().refresh_token_expire_days),
        ),
    )

    user.last_login_at = now
    session.commit()

    return LoginResult(
        access_token=create_access_token(user.id),
        refresh_token=raw_token,
    )

Step 04

Every failure, one parametrized list

The rule under test is that four different failures look identical. One parametrized list holds them: a wrong password, an unknown email, a deactivated account with the right password, and a deactivated account with a wrong one. Two tests run over it: one checks the error and its message, the other that nothing was written.

Each case has to reach the check its name describes. The inactive-user case uses the right password and a real hash, so it fails at is_active and nowhere earlier. With the factory's default hash, which can never verify, it would fail at the password check instead, and deleting the is_active check would leave every test green. Proving it takes a minute: delete the check, run the tests, and watch the inactive-user case fail.

What your code has to do
  1. Save a user with a real hash of a known password in a fixture; the factory's default hash can never sign in.
  2. Check a successful sign-in: the access token decodes to the user, exactly one row holds the hash of the returned token, and the expiry and last_login_at fall between two clock readings.
  3. Check that the email is matched ignoring case and spaces, that two sign-ins create two rows with different tokens, and that a user who must change their password can still sign in.
  4. Run every failure through the same error and message, and through no row and no last_login_at.
  5. Spy on the password check during an unknown-email sign-in: one call, with None for the hash. Then delete the is_active check and see the inactive-user case fail.

Step 05

A cookie that page scripts can't read

The refresh token is the long-lived half of the session, so it never goes in a response body, where page scripts could read it and keep it. It goes in a cookie, and each of the cookie's attributes closes one way to steal or misuse it: HttpOnly against scripts, SameSite=Strict against requests started by other sites, a path limited to /api/v1/auth so it isn't sent with every call, and a Max-Age that matches the token's lifetime.

Secure keeps the cookie off plain HTTP, which is right in production and wrong on your machine: local development runs over HTTP, where the browser would never send a secure cookie back. So the flag follows the environment, and because tests never run as production, one unit test switches the settings to production to cover that branch.

What your code has to do
  1. Name the cookie with one public constant, so sign-in, refresh and sign-out can't disagree about it.
  2. Set the token with HttpOnly, SameSite=Strict, Path=/api/v1/auth, and a Max-Age of the configured days in seconds.
  3. Turn on Secure only in production, reading the settings inside the function so a test can replace them.
  4. Test the production branch: replace get_settings where the function looks it up with a copy of the settings set to production, and check that the header contains Secure.

def set_refresh_cookie(response: Response, token: str) -> None:
    """Send the refresh token to the browser in its protected cookie."""
    settings = get_settings()
    max_age = settings.refresh_token_expire_days * 24 * 60 * 60

    response.set_cookie(
        key=REFRESH_COOKIE_NAME,
        value=token,
        httponly=True,
        samesite="strict",
        path="/api/v1/auth",
        secure=settings.is_production,
        max_age=max_age,
    )

Step 06

The endpoint: a body and a cookie

The router does HTTP and nothing else: it reads the form, calls the service once, puts the refresh token in the cookie and the access token in the body. The form follows the OAuth2 password flow, with the email in a field called username. Clients that speak OAuth2 already know that shape, and plan §8.1 chose it so that Swagger UI's Authorize button can sign in here once routes require a token, later in this issue.

The response model keeps the refresh token out of the body for good: TokenResponse has no field that could hold it, so no later change to the route can return it by accident. Every module's routes then go under one /api/v1 router, included once in the application factory, so the version prefix lives in one place.

What your code has to do
  1. Describe the success body with a schema of two fields: the access token, and a token_type that can only be "bearer".
  2. Get the OAuth2 password form and the database session from FastAPI's dependencies, and call the service once.
  3. Set the refresh cookie on the response FastAPI sends, and return only the access token in the body.
  4. Give the route a summary, its tag, the response model, and its documented 401, as plan §11 asks of every route.
  5. Collect module routers under /api/v1 in one router, include it in the application factory, and check the OpenAPI entry: the form's media type, and the 200, 401 and 422 responses.

    summary="Sign in",

Step 07

Testing over HTTP

The service tests already prove the rules. These tests prove the translation into HTTP: the status codes, the standard error body, the exact keys of the success body, and the cookie's attributes. They go through the whole application, and the client fixture shares the test's database session, so a test can look at the row a request has just written.

Two details trip people up here. A response is not its body: the status and the headers belong to the response, and the JSON comes from response.json(). And response.cookies holds only names and values, what a browser would send back; the attributes are instructions to the browser, and they exist only in the raw Set-Cookie header.

What your code has to do
  1. Check that a successful sign-in answers 200 with a body of exactly two keys, a bearer type, and a token that decodes to the user.
  2. Check that the Set-Cookie header carries every attribute, with Max-Age computed from the settings and no Secure outside production.
  3. Check that the cookie's value is the token whose hash was saved, and that it appears nowhere in the body.
  4. Check that a wrong password gets 401 AUTHENTICATION_FAILED with the generic message and no cookie, writing the status and the code out rather than reading them from the exception class.
  5. Check that a form without a username gets a 422 naming body.username alone, and that the right credentials sent as JSON get a 422 and write no row.
Hint — what this step uses
data= and json=
Form or JSON. data= sends application/x-www-form-urlencoded, which the OAuth2 form expects; json= sends a JSON body.
response.headers["set-cookie"]
The raw header, with every attribute. Lowercase it before searching, because the attributes' capitalization isn't yours to choose.
response.cookies[REFRESH_COOKIE_NAME]
The cookie's value, by name. Indexing raises KeyError when the cookie is missing, so it doubles as a check.
ErrorCode
The published error codes. Comparing with ErrorCode.AUTHENTICATION_FAILED pins the contract; comparing with AuthenticationError.code would agree with any change to the class.

def test_login_returns_a_bearer_access_token(user: User, client: TestClient) -> None:
    """A successful sign-in answers 200 with a bearer token that names the user."""
    response = client.post(LOGIN_URL, data={"username": user.email, "password": PASSWORD})
    body = response.json()

    assert response.status_code == 200
    assert set(body) == {"access_token", "token_type"}
    assert body["token_type"] == "bearer"
    assert decode_access_token(body["access_token"]) == user.id
