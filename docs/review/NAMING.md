# Naming decisions

The vocabulary this codebase uses, so two names never mean the same thing.
Terms come from the project plan's domain model and glossary. Add a row
whenever a review settles a term; never rename against this file.

## Vocabulary

| Use | Not | Why |
|---|---|---|
| medicine | drug, medication | The project plan and the `medicines` table use "medicine" |
| `exc` | `err`, `e`, `ex`, `error` | A caught or handled exception. It is Python's and Starlette's own name for one, and it leaves `error` free for error bodies and Pydantic's error dicts (R-002) |
| `login` in code names: `login`, `last_login_at`, `verify_login_password` | `sign_in`, `signin`, `log_in` | The route is `/auth/login` and the use case is `login`, so names follow them. Docstrings, comments, and messages keep the plan's prose words "sign in" and "sign-in" (run 1, stage 3) |
| `hasher` for what computes a hash, such as `_password_hasher` | `hash` for the hasher | A `*_hash` name holds a stored value, like `users.password_hash` and `refresh_tokens.token_hash`. The hasher used to be `_password_hash`, so `_password_hash.verify(password, password_hash)` read as two hashes (run 1, stage 3) |
| `password_hash` for a password's hash and `token_hash` for a refresh token's, wherever the value appears, stored or not, after the `users.password_hash` and `refresh_tokens.token_hash` columns; several of them are `password_hashes` or `token_hashes` | `hashed_password`, `hash_tokens` | One value, one name: the columns, every parameter that takes the value, such as `verify_password(password, password_hash)`, and `make_user(password_hash=...)` already said `password_hash`. Only `tests/test_security.py` said `hashed_password`, and its set of refresh token hashes was `hash_tokens`, which reads as a verb, until both were renamed to match (run 1, stage 13) |
| `create_<thing>` for a repository function that stores a new row, such as `create_user` | `add` | The repository shape rule lists `create_`, and the name says what is stored. The function only adds the object to the session, and the `INSERT` runs at the next flush, as its docstring says. A service function can share the name, such as the users service's `create_user`, which names the use case; callers write `repository.create_user`, so the two never mix (run 1, stage 5) |
| `data` for a use case's one validated input schema, such as `create_user(session, data: UserCreate)` and `change_password(session, user, data: PasswordChange)`. A changed copy takes a prefix, such as `admin_data` | `user_create`, `user_in`, `payload` | The annotation already names the schema, and each use case takes only one, so the shape rule's "no `data` when a specific word exists" doesn't apply to it. Your choice of my recommendation (run 1, stage 6) |
| `values` for the dict of field values that a model or a schema is built from, such as the dict each factory in `tests/factories.py` fills and the one the schema tests' `_valid_values(**overrides)` returns. The schema built from it is `data`, the row above's name for a validated input schema, as in `data = UserCreate(**values)` | `data` for the dict, and `user` for a `UserCreate` | One name, one meaning: `data` already names a validated input schema, as in `tests/test_user_service.py`'s `data = make_user_create()`, and `user` names an ORM `User` everywhere else. `tests/test_user_schemas.py` called its dict `data` and its `UserCreate` `user` until both were renamed to match, and its helper `valid_data` became `_valid_values`, private like the other test modules' helpers, such as `_make_token`. Your choice of my recommendation (run 1, stage 14). `tests/test_auth_schemas.py` said `valid_password_change` for its helper, `data` for the dict, and `password_change` for the `PasswordChange` until they were renamed to match too (run 1, stage 17) |
| `get_<thing>_by_hash` for a lookup by a `*_hash` column, such as `get_refresh_token_user_id_by_hash` for `refresh_tokens.token_hash`, which returns only the token's `user_id`. A lookup by hash that also locks the row adds `_for_update`, as in `get_refresh_token_by_hash_for_update` | `get_by_hash`, `get_refresh_token_by_token_hash` | The shape rule's `get_<thing>_by_<field>`. The thing already says "token", so repeating it in the field adds nothing; the parameter keeps the column's full name, `token_hash` (run 1, stage 7). The locking lookup was `get_refresh_token_by_hash` until R-030 renamed it to follow the `_for_update` row, your go-ahead (run 1, stage 8 fixes) |
| `get_<thing>_by_<field>_for_update` for a lookup that also locks the row until the transaction ends, such as `get_user_by_id_for_update`, `get_refresh_token_by_hash_for_update`, and `get_refresh_token_by_id_for_update` | `lock_<thing>`, a `lock` or `for_update` flag on `get_<thing>_by_<field>`, and the plain `get_<thing>_by_<field>` for a lookup that locks | The name keeps the shape rule's `get_<thing>_by_<field>` and adds the SQL term for what it does, `FOR UPDATE`, so a reader sees that the call can wait and holds a lock. It is a function of its own rather than a flag, because a boolean parameter would break the `is_`/`has_`/`can_` rule, and the locked read needs `populate_existing`, which the plain lookup avoids. Named with R-022's fix, your go-ahead (run 1, stage 7 fixes). R-030 brought the refresh-token lookup by hash, named before this row, in line (run 1, stage 8 fixes) |
| `revoke_all_<things>_for_<owner>` for a repository function that revokes many rows in one statement, such as `revoke_all_refresh_tokens_for_user` | `revoke_all_for_user`, `update_<things>` | "Revoke" is the plan's word for ending a token (§8.1), and says more than the shape rule's generic `update_`. The name says what is revoked, like `create_refresh_token` and `get_refresh_token_by_hash_for_update`, and "all" keeps the security property in the name: every session of that user ends. Your choice of my recommendation (run 1, stage 7) |
| `access_token` or `refresh_token` for a name that holds a raw token, such as the `access_token` parameter of `get_current_user_allowing_password_change`, with `raw_` in front where a row or hash of the same token is in scope, as in the auth service's `raw_refresh_token`. Plain `token` only where the function's name already says which kind, as in `decode_access_token(token)` and `set_refresh_cookie(response, token)` | `token` where either kind could be meant | Sign-in issues two kinds of token, both strings, so only the name tells a reader which one a value is. The auth service already says `access_token`; the bearer token's parameter in `app/api/deps.py` was `token` until it was renamed to match (run 1, stage 9) |
| `token_row` for the ORM object of a refresh token, the row that stores only its hash, wherever the raw token is in scope too, and `token_rows` for several; a prefix says which row it is, as in `new_token_row` and `other_device_row`. The raw value is `raw_token` or `raw_refresh_token` | `token` and `tokens` for a row where a raw token is in scope | A refresh token exists twice there, as the raw value the client holds and as the row that stores its hash, so the name says which one a value is. The auth service already says `refresh_token_row` and `new_token_row`, and `tests/test_auth_service.py` named its rows this way, except its sign-in tests, which said `tokens` and `token` until they were renamed to match. Where no raw token is in scope, as in `tests/test_auth_repository.py`, which works with rows and hashes only, a row stays `token`, as in `found_token`. Your choice of my recommendation (run 1, stage 18) |
| `db` for the session a route or a dependency receives from `get_db`, as in `db: Annotated[Session, Depends(get_db)]`. Services and repositories call the same object `session`, as in `create_user(session, data)`, so a route reads `service.login(db, ...)` | `database`, and `session` in a route's or a dependency's signature | Every route and dependency already said `db`, after the dependency (`get_db`) and the package (`app.db`) that provide it, and the readiness check said `database` until it was renamed to match. Inside services and repositories, `session` is SQLAlchemy's own name for the object. The plan's glossary doesn't list the abbreviation; it stays as the codebase's established name, your choice of my recommendation (run 1, stage 10) |
| `found_<thing>` for what a lookup returns in a test, the object or `None`, such as `found_user = get_user_by_email(db_session, user.email)`, as `tests/test_auth_repository.py` already said `found_token`. A lookup that returns one column is named after that column, as `found_user_id` holds what `get_refresh_token_user_id_by_hash` returns. A use case is no lookup: what it returns is named after the use case, as `authenticated_user` holds what `get_authenticated_user` returns and `issued_tokens` what sign-in returns | `result`, `database_user`, and a bare `user_id` beside the test's own `user` | The test's own `user` is already the object it saved, so the lookup's answer needs a name of its own, and `assert found_user is user` then reads as the check it is. `tests/test_user_service.py` said `result` until it was renamed to match (run 1, stage 15). `tests/test_user_repository.py` said `database_user` and `result`, and `tests/test_auth_repository.py` `result` and `user_id`, until they were renamed to match too (run 1, stage 16). `tests/test_auth_service.py` said `result` for what `get_authenticated_user` returns until it was renamed `authenticated_user`: the function decodes a token and checks the account, and it raises rather than answering `None`, so `found_user` would call it a lookup (run 1, stage 19) |
| `exc_info` for the `ExceptionInfo` a test gets from `with pytest.raises(...) as exc_info` | `crash`, `excinfo` | pytest's documented name, and the one 49 of the suite's 50 `pytest.raises` blocks already used. It holds the `type`, `value`, and `tb` that `sys.exc_info()` returns, the three values `tests/test_cli.py`'s crash test hands to `sys.excepthook`; that test said `crash` until it was renamed to match. Your choice of my recommendation (run 1, stage 15) |
| `result` for what `CliRunner().invoke(...)` returns, a `click.testing.Result` | `run`, `outcome` | An exception to the shape rule's "no `result`": here it is the library's own type, and the name Click's and Typer's documentation give it, as the shape rule keeps a library's spelling, like `loc`. Your choice of my recommendation (run 1, stage 15) |

## Shape rules

These apply everywhere and are enforced by review, not by a linter.

- Booleans start with `is_`, `has_`, or `can_`.
- Collections are plural; single items singular.
- Repository methods: `get_<thing>_by_<field>` returns one or `None`, `list_<things>` returns many, plus `create_`, `update_`, `delete_`, `exists_`.
- Service methods name the use case: `book_appointment`, not `process`.
- No type names in variable names, and no `data`, `info`, `tmp`, or `result` when a specific word exists.
- Abbreviations only when the plan's glossary defines them (MRN, FEFO).
- A name that mirrors a library's own key keeps the library's spelling, such as `loc` for Pydantic's `error["loc"]` (R-002).
- Tests: `test_<action>_<condition>_<expected>`.
